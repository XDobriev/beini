# Уведомления администратору в Telegram

Реализовано 1 ноября 2026; проверяется mock transport и loopback Bot API.
Реальных реквизитов, отправок сообщений и проверки закрытой группы в этой задаче нет.

## Поведение

Источник — `orderstate.NotificationQueue()` и сохранённый `notificationSource`:
состав и цены определены сервером, контакты нормализованы до записи заказа.
Отдельный worker доставляет pending, затем confirmed или rejected. Даже если
касса ответила сразу или итог восстановлен после рестарта, порядок сохраняется.
Ожидание не означает отказ; сообщение просит сверить кассу и не дублировать заказ.
Подтверждение создания не означает оплату, фискализацию или прочтение сообщения.

ID события — `orderId:status`. Карточка содержит способ получения, имя, телефон,
адрес, комментарий, все позиции, сумму и UTC-время события. Используется plain text,
без HTML/Markdown и предпросмотра ссылок. Длинная карточка разбивается без потери
позиций на части до лимита sendMessage; каждая часть содержит ID/номер.

`notifications.jsonl` в `BEINI_STATE_DIR` — независимый append-only журнал
с checksum, fsync и OS lock на основе orderstate.Store. В нём только хеши ключей
событий/группы, служебные ID, счётчик попыток, срок retry и ack; копий контактов нет.
Состав остаётся в `orders.jsonl`. ACK фиксируется после валидного успешного ответа
Bot API с message_id. Повтор события, опрос статуса и рестарт не переотправляют
части с сохранённым ack. У конечного события нет обхода недоставленного pending.
Формат карточки и границы частей являются частью контракта дедупликации:
их изменение требует продуманной миграции receipts, а не сброса журнала.

Перед сетью сохраняются попытка и срок повтора. Backoff 2, 4, 8…512 секунд;
429 учитывает больший retry_after (защитный предел 24 часа). Пауза всего transport
тоже сохраняется, чтобы следующие заказы не обходили ограничение группы.
Интервал считается после ответа transport. Общая пауза фиксируется раньше
срока отдельной части: остановка между этими записями не снимает ограничение группы.
400/401/403 и прочие постоянные 4xx не удаляют событие: повтор через 15 минут
до исправления реквизитов/прав. 408 и сетевые/5xx ошибки используют backoff.
Один worker, HTTP timeout 8 секунд, контекст отправки 10 секунд, запрет redirects.
Shutdown отменяет отправку и ожидает worker до закрытия receipts.

Ограничение внешнего API: потеря ответа после принятия Telegram или остановка
между sendMessage и fsync ack может дать повтор той же части с тем же ID.
Exactly-once доставки не обещается. Повторная карточка не означает новый заказ.
Без реквизитов worker не запускается и фиктивных ack нет; backlog сохраняется.
После включения будут отправлены также накопленные события старых заказов с source.
Старые записи без source автоматически не восстанавливают состав.

## Создание бота и закрытой группы

Эти шаги выполняет владелец; код сам не создаёт группу/бота и не запрашивает updates.

1. В официальном [BotFather](https://t.me/BotFather) выполните `/newbot`, задайте
   имя и username. Полученный токен сохраните в секретном окружении серверного
   сервиса. Не вставляйте его в Git, frontend, скриншоты, чат или URL браузера.
   При утечке перевыпустите токен через BotFather.
2. Создайте **закрытую группу** с владельцем и администратором. Добавьте бота,
   разрешите ему отправлять обычные сообщения. Права администратора для самой
   отправки не требуются; проверьте ограничения группы. Не делайте группу публичной.
   Privacy Mode можно оставить включённым: чтение переписки сервису не нужно.
3. Напишите в нужной группе `/beini_setup@username_вашего_бота`. В новой установке
   без webhook получите ID через getUpdates с **сервера**, не сторонним ботом.
   Пример ниже читает токен из окружения, печатает только ID групп с этой командой
   и не создаёт сообщений или заказов. Если updates пусты, повторите команду
   в группе и проверьте username/права. Если уже есть webhook/другой consumer,
   согласуйте получение ID с его владельцем; не удаляйте webhook вслепую.
4. Запишите отрицательный ID именно этой группы в `TELEGRAM_CHAT_ID`.
   Для supergroup он обычно начинается с `-100`. Не используйте публичный username.
5. По отдельному согласованию включите сервер с реквизитами и проведите проверку
   доставки в группе на mock-заказах, затем согласованную кассовую приёмку.
   Запуск с накопленным журналом отправит backlog реальных сохранённых контактов:
   заранее проверьте состав группы и историю backlog. Реальный checkout не нужен
   для первичной проверки transport.

Пример получения ID, выполнять только при настройке, не в автопроверках:

```python
import json
import os
import urllib.error
import urllib.request

request = urllib.request.Request(
    "https://api.telegram.org/bot" + os.environ["TELEGRAM_BOT_TOKEN"] + "/getUpdates",
    data=b'{"timeout":0,"allowed_updates":["message"]}',
    headers={"Content-Type": "application/json"},
)
try:
    with urllib.request.urlopen(request, timeout=10) as response:
        result = json.load(response)
except (urllib.error.URLError, TimeoutError):
    raise SystemExit("Не удалось получить updates; проверьте токен и соединение") from None
ids = set()
for update in result.get("result", []):
    message = update.get("message", {})
    chat = message.get("chat", {})
    if (chat.get("type") in ("group", "supergroup")
            and message.get("text", "").split("@", 1)[0] == "/beini_setup"):
        ids.add(chat["id"])
for chat_id in sorted(ids):
    print(chat_id)
```

Официальные источники: [управление ботом](https://core.telegram.org/bots/features#botfather),
[Privacy Mode](https://core.telegram.org/bots/features#privacy-mode),
[sendMessage](https://core.telegram.org/bots/api#sendmessage),
[getUpdates](https://core.telegram.org/bots/api#getupdates),
[retry_after](https://core.telegram.org/bots/api#responseparameters).

## Конфигурация и эксплуатация

Только окружение процесса Go:

- `TELEGRAM_BOT_TOKEN`: секрет от BotFather.
- `TELEGRAM_CHAT_ID`: одна закрытая группа (отрицательный числовой ID).
- `BEINI_STATE_DIR`: существующий постоянный каталог вне checkout и STATIC_DIR.

`.env` автоматически не читается. Значения Telegram не читаются из JSON и не
сериализуются Config. Не передавайте их в JavaScript, /demo или HTTP-ответы.
Старый план 30 октября с TELEGRAM_CHAT_IDS, JSON-токеном, Noop и тремя retry
является историческим; текущий контракт описан здесь.

Пустая/неполная/неверная конфигурация, ошибка открытия receipts или несовпадение
группы отключают только уведомления и пишут безопасный лог. Оформление продолжается,
источник остаётся в orders. При runtime ошибке записи receipts worker не отправляет
новые сообщения без сохранённой попытки; после устранения причины нужен рестарт.
Логи содержат ID события и номер попытки, без токена, URL Bot API и контактов.
Health процесса не доказывает доставку: контролируйте логи worker и проверку группы.

Первый запуск привязывает notifications.jsonl к хешу ID группы. Случайная смена
TELEGRAM_CHAT_ID блокирует доставку до сверки. При миграции группы (включая upgrade
в supergroup) остановите worker, сохраните оба журнала, согласуйте новую группу
и решение о переносе backlog/ack. Автоматического переноса и сброса привязки нет.
Удаление/откат receipts заново отправит историю, удаление orders опасно дублями кассы.
Ротация токена того же бота и группы не сбрасывает ack.

Нужны ACL учётной записи сервиса, ограниченный состав группы и защищённые backups.
Retention контактов/истории и порядок очистки ещё требуют решения владельца;
автоматической очистки нет. Не усекать orders или receipts вручную при работающем
процессе. Поддерживается один процесс на локальном диске; реплики с разными
журналами не обеспечивают дедупликацию.

## Offline-проверки

`go test ./internal/notifier ./internal/orderstate ./cmd/server ./internal/config`
и `python scripts/check.py`. Тесты подставляют transport и локальный httptest Bot API,
не используют настоящие Telegram/iiko реквизиты. Покрывают retry/ack/restart,
частичные карточки, потерю ack, 429, panic/таймаут/ошибки, отсутствие обхода pending,
неблокирующий заказ и shutdown. UI в этом изменении не меняется.
