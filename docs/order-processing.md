# Обработка заказов: контракт и подключение

Срез интеграционной версии: 1 ноября 2026. Файловый журнал, маршруты статуса
и меню, frontend polling подключены в приложении. Проверено с mock API.
Telegram transport подключён и проверен через mock; боевой тест не выполнялся.

## Состояния

| `status` | Условие | Конечное |
|---|---|---|
| `confirmed` | iiko вернул `creationStatus=Success` для сохранённого ID | Да |
| `pending` | `InProgress`, неизвестный статус, ошибка сети/авторизации/JSON/HTTP, заказ ещё не найден | Нет |
| `rejected` | iiko вернул `Error` или `Cancelled` для сохранённого ID | Да |

Это состояния **создания** заказа. Они не описывают приготовление, доставку,
оплату или фискализацию. `confirmed` не означает, что администратор прочитал заказ.
Неизвестный статус никогда не становится подтверждением.

Перед внешним вызовом сервер сохраняет UUID в журнал и передаёт его в `order.id`.
За данным ключом закрепляется только одна попытка create. Worker опрашивает
`/api/1/deliveries/by_id` при запуске и затем каждые 5 секунд; отдельный запрос
ограничен 10 секундами. Опрос последовательный, поэтому при большом числе
ожидающих заказов цикл занимает дольше 5 секунд. Ошибка опроса оставляет последнее
наблюдение. Опрос продолжается без предельного срока до конечного результата
или остановки handler. Терминальный результат больше не опрашивается.

`outcomeUnknown=true` означает, что нет достоверного наблюдения `InProgress`
или конечного статуса: неизвестно даже, принял ли iiko попытку создания.
`false` при `pending` означает наблюдавшийся `InProgress`, а не подтверждение.
Поле не является индикатором свежести связи с кассой.

## POST /api/order

Тело запроса, серверная валидация, проверка каталога и ограничения размера
сохранены. Заголовки `Idempotency-Key` и запасной `X-Idempotency-Key` поддерживаются;
первый имеет приоритет. Ключ после удаления пробелов по краям — 1–128 байт.

Клиент должен создать случайный ключ с минимум 128 битами энтропии **до отправки**
и сохранить ключ вместе с точными байтами JSON. Для повтора нужны те же байты,
включая пробелы, и тот же ключ. Одинаковый JSON с другим форматированием считается
другим телом. Ключ является секретом доступа к статусу; не передавайте его в URL.

Без ключа запрос по-прежнему принимается: сервер генерирует ключ и возвращает
его в заголовке `Idempotency-Key`. Если ответ полностью потерян, клиент без
собственного ключа не сможет восстановить эту попытку. Каждый новый запрос
без ключа или с новым ключом — самостоятельный заказ, возможен дубль.

Повтор возвращает **текущее сохранённое состояние**, включая обновлённый итог,
с `X-Cache-Lookup: HIT`. Это не неизменный кэш первоначального HTTP-ответа.
Одновременный повтор возвращает `pending` без второго create. Повтор другого тела
с тем же ключом возвращает 422. Повтор после смены меню не пересчитывает заказ.
Срока истечения ключей в хранилище заказов нет.

Поля старого ответа сохранены: `success`, `pending`, `correlationId`,
`creationStatus`, `totalSum`, `orderInfo`. Новые поля: `status`, `outcomeUnknown`,
`orderId`, `message`. `orderId` — UUID попытки, совпадающий с переданным iiko ID;
`orderInfo.id` содержит этот ID даже до подтверждения его существования в iiko.
`correlationId` может быть пустым при потере ответа create; `creationStatus`
может быть пустым или неизвестным. Внешние тексты `errorInfo` не выдаются гостю.

Пример ожидания после потерянного ответа iiko:

```json
{
  "success": true,
  "pending": true,
  "status": "pending",
  "outcomeUnknown": true,
  "orderId": "9dc10e2a-493b-4a33-a78a-e9b0d3fa6fb7",
  "correlationId": "",
  "creationStatus": "",
  "totalSum": 590,
  "orderInfo": {
    "id": "9dc10e2a-493b-4a33-a78a-e9b0d3fa6fb7",
    "creationStatus": ""
  },
  "message": "Заказ ожидает подтверждения кассы"
}
```

| HTTP | Значение |
|---|---|
| 200 | `confirmed` или `pending`; различать по `status` / `pending` |
| 422 | `rejected` с `success=false` и безопасным `error`; либо конфликт тела с ключом (без `status`) |
| 400/413/415 | Ошибка входных данных; новая попытка не записывается |
| 503 | Нельзя прочитать/зафиксировать состояние или handler останавливается; повторять с тем же ключом и телом |

Сетевой сбой create теперь возвращает 200 с `pending=true,outcomeUnknown=true`
вместо прежнего 502, освобождавшего ключ. Это намеренное уточнение семантики
при сохранении формы API. Запрос к iiko продолжается при disconnect клиента,
ограничен отдельным timeout 35 секунд и отменяется при `OrderHandler.Close()`.
Ошибка записи результата после успешного iiko даёт 503, а сохранённая до отправки
попытка позволяет сверить результат после восстановления.

## GET /api/order/status — новый маршрут

`OrderHandler.OrderStatus` зарегистрирован в сборке приложения. Нужен исходный ключ в одном
из указанных заголовков; тело не требуется. Форма результата и коды 200/422
те же, что у POST; 400 — нет корректного ключа, 404 — ключ неизвестен,
405 — другой метод, 503 — хранилище недоступно. Этот GET только читает журнал,
самостоятельно iiko не вызывает. Ответы состояния имеют `Cache-Control: no-store`,
ожидание — `Retry-After: 5`. Клиент должен читать JSON также при HTTP 422.

Legacy POST /api/test-order сохраняет ограничения доступа по X-Test-Token / loopback
и использует тот же журнал и worker для фиксированного тестового заказа.
В main с динамическим каталогом он отключён (503), потому что фиксированного
Латте нет в allowlist. Legacy handler в тестах также поддерживает повтор с ключом и возвращает перечисленные поля,
включая `message`, соответствующий фактическому состоянию. Это реальный заказ;
автопроверки используют только mock iiko.

## Контракт для frontend и Telegram

- Сохранять ключ и тело до отправки. После timeout, 503, потери ответа или
  `pending` использовать тот же ключ; не создавать автоматически новый заказ.
- `success=true` сохранён для совместимости и не означает подтверждения:
  сообщение об успехе допускается только при `status=confirmed`.
- При `pending` показывать ожидание; `outcomeUnknown=true` требует особенно
  осторожного текста: результат неизвестен, повторное оформление может дублировать заказ.
- Получать итог через GET с тем же ключом, учитывать Retry-After и сетевой backoff.
- Для уведомления смены различать все три `status`; группировать
  сообщения по `orderId` и сохранять собственную дедупликацию/очередь уведомлений.
  HTTP endpoint не является outbox; локальная NotificationQueue описана ниже.
- Журнал хранит защищённый источник состава/контактов для уведомлений.
  GET статуса их не возвращает; чтение доступно только локальному сервису.

Frontend интегрирован: pending/unknown блокируют новый заказ, сохраняют ключ/тело
и получают итог polling. Confirmed и rejected отображаются отдельно.

## Подключение в приложении

`cmd/server/application.go` открывает журнал `BEINI_STATE_DIR/orders.jsonl`,
подключает `NewOrderHandlerWithState` и регистрирует GET статуса с отдельным limiter.
BEINI_STATE_DIR обязателен: абсолютный существующий каталог вне web root,
с разрешением symlink/junction при проверке. Порядок закрытия: menu worker,
handler (worker/create), Store. Старые конструкторы в тестах используют память.
Прямые утилиты iiko не получают этих гарантий; cmd/test-order остаётся живым действием.

Динамический каталог фиксируется одним `Store.Pin()` на новый заказ. В JSON
ожидается `expectedPrices`: цены строк в том же порядке, что `items`. При отличии
любой цены (или отсутствии массива) сервер возвращает 409 `code=price_changed`,
`items` с доверенными ценами и `totalSum`. Попытка не резервируется, create не
вызывается. После явного подтверждения гость посылает новый согласованный запрос;
сервер снова проверяет цены. Уже сохранённый повтор проверяется раньше меню/цен,
поэтому окончательный статус доступен даже при просроченном меню.

Frontend сохраняет key/body в localStorage **до сети**; при невозможности записи
отправка блокируется. GET выполняется с Retry-After и backoff 5–60 секунд, также
после refresh. 404 или сетевой сбой разрешает только ручной повтор сохранённых key/body.
Terminal response заменяет browser body записью ключа/статуса без контактов.
Новая корзина после успеха закрывает прежнюю попытку. Корзина хранит ожидаемые цены;
обновление цены до отправки требует отдельного согласия гостя.

## Локальный источник уведомлений

ADR [0004](decisions/0004-integration-contracts.md) дополняет исходное решение 0002.
`ReserveWithNotification` атомарно с pending сохраняет нормализованный состав,
имя, телефон, адрес и комментарий в поле `notificationSource`. Никаких токенов
или исходного Idempotency-Key там нет. GET статуса не возвращает источник.
`NotificationQueue()` восстанавливает все события pending и конечного результата
с ID `orderId:status`; повтор и рестарт не создают новый ID. Для исторических записей
без источника очередь пустая — состав восстановить из такого журнала нельзя.

Worker internal/notifier читает эту очередь; отдельный notifications.jsonl хранит
ack частей и сроки retry, фильтрует доставленные события и сохраняет порядок
pending/итога после рестарта. Ошибка transport/receipts не блокирует оформление.
Без реквизитов сообщения не отправляются; контакты хранятся бессрочно. Retention
ещё требует решения, доступ ограничивается ACL. Контракт и ограничение дублей
при потере ответа Telegram: [уведомления](telegram-notifications.md).

## Хранение и границы гарантий

Журнал append-only: полная JSON-строка с SHA-256, `Sync()` до изменения памяти
и отправки create. Последний незавершённый хвост отсекается при Open;
повреждённая полная строка блокирует открытие. При ошибке записи/Sync Store
блокирует дальнейшие чтения/создания до переоткрытия. OS lock предотвращает
второго writer этого файла на Windows и Unix (Linux/macOS/BSD).

После рестарта все незавершённые записи доступны только для сверки; сервер
**не повторяет create**, даже если процесс остановился между записью и реальной
отправкой. Такой заказ может остаться pending навсегда. Авторизация могла
завершиться ошибкой ещё до create — эта консервативная реализация также оставит
попытку неопределённой. Отсутствие ID в by_id не доказывает, что заказ не появится
позже. Повторный заказ с новым ключом допускается только после ручной сверки
со сменой и осознанного решения владельца сценария.

В пределах сохранённого журнала и одного ключа шлюз выполняет не более одного
вызова create; HTTP redirects отключены. Это **не exactly-once в iiko** и не
обещание отсутствия дублей: новый/потерянный ключ, удалённый/откаченный журнал,
независимые процессы с разными файлами, повтор на стороне proxy/iiko, потеря диска
или неподтверждённое поведение внешнего API выходят за эту гарантию.
Заданный клиентом `order.id` используется для последующей сверки, а не как
предположение об идемпотентности create на стороне iiko.

Гарантия fsync проверена тестами как восстановление после остановки процесса;
отказ питания/диска, сетевые файловые системы и резервное копирование отдельно
не испытывались. В частности, создание нового файла не сопровождается fsync
родительской директории. Старую резервную копию нельзя считать безопасной заменой
актуального журнала без сверки заказов. Автоочистки/компактации нет: журнал растёт,
все записи загружаются в память. Не удалять ключи по таймеру. Для нескольких
реплик/большого потока нужна общая транзакционная БД и отдельная миграция.

Семантика creationStatus сверяется с [документацией iiko](https://api.iiko.help/docs/guides/webhooks/).
Поддержку переданного order.id и полноту by_id на конкретной версии и терминале
нужно подтвердить отдельным согласованным живым тестом; mock-тесты этого не доказывают.
