# Переход загрузки меню на iiko API v3

> Реализовать последовательно в текущей сессии; коммит и публикация отдельно.

Цель: восстановить проверяемое меню после наблюдаемого HTTP 410 старого метода.
Владелец согласовал привязку существующего меню и обновление приложения.

Подход: отдельный адаптер v3 нормализует товары в существующий контракт menusync;
витрина и правила checkout сохраняются. ID меню и опциональная ценовая категория
задаются в конфигурации/ENV. Неподдерживаемые размеры, модификаторы, расписания,
вес и открытая цена не превращаются в обычные продаваемые позиции. Отказ/неполный
ответ сохраняет последний корректный снимок, но не снимает стопы.

- [x] Добавить падающие HTTP/адаптер-тесты: новый путь/тело, цены, скрытые и неоднозначные
  позиции, неполные ответы; привязка к ID меню и отсутствие старого метода.
- [x] Реализовать адаптер, параметры конфигурации и привязку дискового кэша к источнику.
- [x] Перевести mock сборки приложения на новый контракт и проверить restart/order.
- [x] Обновить документацию и выполнить python scripts/check.py.
- [x] Запустить реальную сборку локально, проверить /api/menu и один согласованный
  тестовый самовывоз. Не повторять create при неопределённом исходе.

Результат теста: один POST, pending → confirmed/Success, UI подтвердил 590 ₽.
Карточка №12540 подтверждена скриншотами iikoFront; отмена фиксируется отдельно в live-check.

Риски для проверки: одинаковый продукт с разными ценами; скрытые группы/размеры;
расписание, которого сайт пока не учитывает; подмена ID меню в ответе; восстановление
кэша другого меню. V3 не содержит legacy revision: значение 0 означает отсутствие
версии поставщика, свежесть определяется временем успешной загрузки.
