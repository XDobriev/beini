# Тестовая эксплуатация BEINI

Дата: 2 ноября 2026. Основа: origin/main 38aad78; изменения локальные.
Продуктовый подход утверждён подробным поручением владельца.

## Поведение

Одно приложение, один orders.jsonl. Режим ENV `BEINI_ORDER_MODE`:
`closed` (по умолчанию), `tester`, `public`. Неизвестный режим блокирует запуск.
GET статуса по приватному ключу работает независимо от режима и сессии.
POST всегда проходит проверку доступа перед существующим CreateOrder, без
обхода бизнес-валидации. Закрытый доступ не резервирует ключ.

Гостям доступны меню, поиск и корзина. В шторке вместо отправки — объяснение
и звонок +79204827777. Плашка над шапкой отражает режим; вошедший владелец
видит предупреждение о реальной отправке. При public плашка о закрытии скрыта.
Страница `/tester` содержит пароль и выход, возвращает к обычной витрине.

## Авторизация

ENV `BEINI_TESTER_PASSWORD_HASH` хранит PBKDF2-HMAC-SHA256 с 600000 итераций,
случайной солью 16 байт и производным ключом 32 байта. Используется стандартный
`crypto/pbkdf2` Go 1.24; сравнение constant-time. Утилита читает пароль со stdin,
в аргументы/URL/исходники пароль не попадает. Без хеша вход отключён; неверный
формат блокирует запуск. Новых внешних зависимостей нет.

Случайные opaque session ID, на сервере только SHA256 ID и срок 8 часов.
Cookie `__Host-beini_tester`, HttpOnly, Secure, SameSite=Strict, Path=/, без Domain.
После logout сессия удаляется. Restart и смена хеша отзывают все сессии.
Dev HTTP разрешён только при явном `BEINI_TESTER_LOCAL_HTTP=1`, только для
loopback Origin/Host и прямого loopback без proxy headers; иное блокирует доступ.

GET `/api/access` no-store возвращает режим, допуск, признак mock, срок сессии
и CSRF-токен. CSRF: краткоживущая подписанная привязка к HttpOnly cookie,
проверка Origin/Fetch-Metadata, заголовок X-CSRF-Token для login/logout/order.
Токены в памяти вкладки, не localStorage. Login ограничен глобально (все IP)
и числом параллельных KDF: 5 попыток/мин; это защищает и за reverse proxy.
Отдельный IP limiter не считается единственной защитой от перебора.

## Восстановление и разработка

Frontend перепроверяет access при focus/visibilitychange, каждые 30 секунд и
перед POST. Logout уведомляет соседние вкладки без хранения секретов.
Истечение доступа не удаляет key/body попытки; polling продолжается.
Повтор возможен после входа, только с прежними key/body, явным действием.
Доступ и свежесть меню — разные условия с разными сообщениями.

`scripts/mock-ui.py` — loopback fixture без iiko config/ключей, с тем же HTTP
контрактом access/login/logout и синтетическим checkout. Всегда заметная
надпись mock, без утверждения о принятии рестораном. Go integration tests
проверяют реальную сборку приложения и mock iiko, постоянный журнал/restart.

## Проверки

До/после `python scripts/check.py` с loopback. Проверить закрытие всех режимов,
ошибки пароля/лимитер, CSRF, forged/expired/logout/restart, отсутствие секретов,
ноль upstream create у гостей, owner price/stop/pending/confirmed/rejected/
lost response/replay. Node VM проверяет сохранение попытки и frontend gate.
Браузер desktop/mobile: вход/выход, звонок, корзина, оба типа, клавиатура,
overflow, mock success/pending/rejected/drop/replay, refresh и несколько вкладок.

Публикация, VPS restart, push и реальные заказы не входят в поручение.
