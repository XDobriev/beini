## Обязательные задачи интеграции

1. cmd/server/main.go: сейчас используется NewOrderHandlerWithDeps и память; нет GET /api/order/status и /api/menu. Подключить файловый журнал, worker меню, маршруты и корректное завершение. Постоянные файлы хранить вне каталога публичной статики.
2. js/app.js frontend worktree: pending/unknown блокируют отправку, но GET статуса отсутствует. Даже если worker подтвердит заказ позже, страница не узнает итог. Подключить опрос, восстановление после refresh, backoff и обработку confirmed/rejected; повтор безопасно выполняется только с прежним ключом/телом.
3. js/app.js читает только MENU_DATA. Подключить /api/menu, свежесть, доступность и обновление корзины. Статический fallback не должен разрешать заказ при недоступном/просроченном серверном меню.
4. handler проверяет позиции через h.catalog. При динамическом каталоге зафиксировать Store.Pin() один раз на проверку всего заказа, чтобы не смешивать цены разных снимков.
5. Проверить несовпадение цены корзины и серверной цены до создания заказа: сейчас клиент отправляет только ID/amount и показывает totalSum уже после создания. Нужен контракт подтверждения изменения цены.
6. Сверить адаптер меню с официальной схемой или согласованным read-only ответом ресторана: fixtures синтетические. Размеры, весовые блюда и любые модификаторы адаптер блокирует; проверить, какие реальные блюда это исключит.
7. Проверить отказы, повторы, восстановление после рестарта и сценарий pending -> confirmed/rejected на совместной версии через mock API.
8. Для Telegram подготовить сохраняемый источник состава/контактов и очередь: журнал orderstate намеренно не хранит эти данные, поэтому одного GET статуса для уведомления после рестарта недостаточно.
