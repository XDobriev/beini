# 0002: Журнал попыток создания заказа и сверка неопределённого результата

Дата: 1 ноября 2026. Статус: принято для серверных пакетов; подключение в main
передано интегратору по границам задачи.

## Контекст

Кэш HTTP-ответа с TTL терялся при рестарте. Ошибка create освобождала ключ,
хотя заказ мог уже существовать в iiko. Pending кэшировался без дальнейшего опроса.

## Решение

До внешнего create сохранять UUID, хеш ключа/тела, сумму и pending в append-only
файл с fsync и OS lock. Передавать UUID в order.id. Создание отделить от опроса,
последующие наблюдения сохранять. После рестарта только сверять сохранённые ID;
не выдавать право повторного create. Конечные состояния неизменны, TTL нет.
Ошибку сети/HTTP/JSON и отсутствие ID в by_id оставлять неопределённостью.
Сохранять API и добавлять явные status/outcomeUnknown и GET статуса.

## Альтернативы и последствия

- Повторять create после timeout: риск дубля при уже созданном заказе; отклонено.
- Считать отсутствие в by_id отказом: eventual consistency не позволяет такого вывода.
- SQLite/общая БД: предпочтительно при нескольких репликах и росте потока,
  но требует зависимости и отдельного подключения/миграции. Для текущего одного
  процесса выбран минимальный файловый журнал без runtime-зависимостей.

Цена консервативности — возможность бессрочного pending, включая остановку
до отправки и ошибку авторизации. Нужна ручная сверка; exactly-once внешнего сервиса
не заявляется. Журнал растёт без автоматической очистки и не содержит данных
для полного уведомления о составе заказа после рестарта. Telegram/outbox не входят.

Реализация: internal/orderstate, internal/handler/order_tracking.go,
internal/iiko/client.go. Контракт, ограничения и шаги интеграции:
[order-processing.md](../order-processing.md).
Проверки: mock iiko, потеря обоих ответов, concurrent replay, конечные статусы,
рестарт, остановка до отправки, недоступность записи, checksum/неполный хвост,
эксклюзивный writer и отсутствие истечения активного lock.
