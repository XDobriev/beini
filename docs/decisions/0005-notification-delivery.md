# 0005. Независимый журнал доставки уведомлений

Дата: 1 ноября 2026. Статус: принято для реализации порученного этапа.

Источник событий и контактов уже атомарно хранится в orders.jsonl. Добавлять
сеть или обязательный ack в транзакцию оформления нельзя: сбой Telegram не
должен влиять на заказ. Повторы после рестарта требуют устойчивых receipts.

Выбран отдельный notifications.jsonl на основе проверенного orderstate.Store:
checksum, fsync, OS lock, отсечение неполного хвоста и fail-closed запись.
Память/noop теряют ack; запись ack в orders связывает сбой уведомлений с заказом;
внешняя очередь сейчас не нужна. В Record добавлены attempts/nextAt для delivery
записей; они используются только отдельным журналом. Контакты туда не дублируются.

Один worker, одна группа, привязка к хешу ID группы. ID события orderId:status,
часть карточки имеет устойчивый ключ eventId:part:index. Pending доставляется
целиком перед итогом; фиксируются ack частей, попытки и transport cooldown.
Сетевые сбои — backoff, постоянные ошибки — редкий retry без удаления события.

ACK появляется только после валидного успешного sendMessage. Telegram не даёт
ключ идемпотентности sendMessage: потеря ответа/crash до fsync ack допускают повтор.
Эту границу невозможно закрыть локальной транзакцией. ID события виден в карточке.

Не реализованы автоматический retention и миграция группы. Изменение формата
разбиения карточки требует сохранения совместимости receipts. Гарантии одного
процесса/локального диска не распространяются на независимые реплики.
