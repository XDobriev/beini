## Локальный запуск

Скопируйте iiko_config.example.json в iiko_config.json. Создайте постоянный
каталог вне checkout/STATIC_DIR, ограничьте ACL учётной записью сервиса и задайте
абсолютный путь в BEINI_STATE_DIR. Затем запустите:
```sh
go run ./cmd/server
```
Сервер читает JSON и затем переопределяет значения из ENV. Если JSON отсутствует,
нужны ENV-параметры интеграции. Примерные значения позволяют посмотреть витрину,
но не выполнять заказ. .env сервер автоматически не читает.

Параметры: BEINI_STATE_DIR, PORT, HTTP_LISTEN_ADDR, STATIC_DIR, IIKO_API_BASE_URL, IIKO_API_KEY, IIKO_APP_ID,
IIKO_CLIENT_SECRET, IIKO_ORGANIZATION_ID, IIKO_TERMINAL_GROUP_ID, DELIVERY_CITY,
TRANSPORT_TIMEOUT_SEC, TEST_ORDER_TOKEN, ALLOWED_ORIGINS, TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID.
Типы заказов и оплаты задаются в JSON. Источник точной схемы:
internal/config/config.go и iiko_config.example.json.

Для меню обязательны `externalMenuId` в JSON или `IIKO_EXTERNAL_MENU_ID` в ENV.
Опциональная ценовая категория: `priceCategoryId` / `IIKO_PRICE_CATEGORY_ID`;
пустое значение использует базовый прайс внешнего меню. Меню должно быть назначено
API-ключу в iikoWeb. Отсутствие ID блокирует запуск с понятной ошибкой.
После смены ID меню или ценовой категории старый дисковый снимок не восстанавливается:
сначала требуется успешное обновление меню и стоп-листа. Журнал заказов не очищать.

Боевые секреты хранятся локально или в механизме секретов окружения.
Не помещайте их в документацию, diff, screenshot и логи проверок.

## Постоянное состояние

`cmd/server/application.go` открывает `BEINI_STATE_DIR/orders.jsonl`, восстанавливает
`menu-cache.json`, подключает worker меню и GET `/api/menu`, `/api/order/status`.
Каталог должен существовать; относительный путь или путь внутри web root (после
разрешения symlink/junction) блокирует запуск. Журнал не заменяется памятью.
В Windows права 0600 не заменяют ACL. Каталог не должен быть публичным или общим.

**Журнал теперь содержит персональные данные:** нормализованный телефон, имя,
адрес, комментарий и состав. Они нужны источнику уведомлений; при включённом
Telegram отправляются в настроенную закрытую группу, но не возвращаются GET статуса. Retention/очистка
ещё не реализованы. Перед публичной эксплуатацией согласовать доступ, срок хранения
и резервирование. Не публиковать журнал и его резервные копии, не помещать в Git.

Хранить на постоянном локальном диске; один процесс/writer. Нельзя обходить OS lock
вторым журналом для той же организации, откатывать старую копию или очищать ключи
без сверки с iiko. Журнал и кэш привязаны к конфигурации организации/терминала;
смена конфигурации требует отдельного хранилища и согласованной сверки.

Безопасный offline стенд UI: `python scripts/mock-ui.py`, порт 8765 loopback-only.
Он не читает конфигурацию iiko. `/__mock__` управляет только синтетическими данными.
Фактический restart с диском проверяется Go-тестом `TestApplicationMenuOrderRestart`.
Фиксированный `/api/test-order` в динамической сборке отвечает 503; кнопка /demo
отключена до отдельного согласования диагностического блюда и цены.

Подготовлены unit systemd, отдельный Nginx-vhost, loopback bind и изолированный

## Проверки после развёртывания

- GET /api/health проверяет живость процесса, не кассу.
- Проверьте главную, фотографии, логотипы и корректные 404 для ассетов.
- Подтвердите HTTPS, CORS и корректное определение IP за выбранным reverse proxy.
- Проверьте restart, логи и сохранность конфигурации.
- Зафиксируйте commit/образ, время проверки и ответственного.
- Разрешение на изменение кода не означает поручение на развёртывание.

## Живой тест кассы

Только по явному поручению на живой тест с координацией персонала:
1. Подтвердите ресторан, терминал, активную смену и присутствие сотрудника.
2. Согласуйте один тестовый заказ и способ его отмены.
3. В режиме `tester` войдите на `/tester` и используйте обычный checkout.
   В динамической сборке кнопка /demo выключена, /api/test-order не настроен
   для текущего меню. Legacy cmd/test-order/tools/test_order.py — отдельные

4. Проверьте карточку заказа, сигнал и печать, если она настроена.
5. Сотрудник отменяет тестовый заказ; зафиксируйте итог без данных гостей.

Все эти способы создают настоящий заказ. /api/test-order доступен по
X-Test-Token, если он задан, иначе — с прямого loopback без proxy-заголовков.

он не повторялся. Подробный исторический регламент: ../TESTING_IIKO_FRIDAY.md.

## Сбой и откат

При неопределённом результате сначала сверьте заказ с кассой; повторная
отправка с новым ключом может создать дубль. Текущий журнал идемпотентности
сохраняется после рестарта; память сессий входа отзывается. Не перезапускайте
процесс как способ повторить заказ.

Порядок отката текущего VPS-окружения: [развёртывание](deployment.md#обновление-и-откат).
Это первый проверенный runtime-релиз: при аварии остановить только beini
и вернуть только его vhost на 503, выполнив nginx -t перед reload.
Сохранить /var/lib/beini целиком; orders.jsonl и notifications.jsonl
не удалять и не откатывать. Другие проекты не перезапускать.

## Тестовая эксплуатация и вход владельца

Реализовано 2–3 ноября 2026. По последующему поручению владельца опубликовано
3 ноября как runtimea66e485 в режиме tester; пароль создан и сохранён закрыто,
HTTPS/вход/выход/desktop/mobile проверены без заказа. [Результат](tasks/test-operation.md).
Актуальная исходная база — origin/main38aad78. При read-only проверке перед
реализацией VPS использовал runtime8651622, публичное API —251 позицию. Это
подтверждение версии меню, а не разрешение гостевой отправки новой версии.

| BEINI_ORDER_MODE | Кто может отправлять новый заказ |
|---|---|
| closed (значение по умолчанию) | Никто, включая вошедшего владельца |
| tester | Только владелец с действующей серверной сессией |
| public | Гость или владелец с корректной CSRF-проверкой |

Неизвестный режим, неверный формат хеша или LocalHTTP блокируют запуск.
Без `BEINI_TESTER_PASSWORD_HASH` вход отключён; `tester` никого не допускает.
`public` является явным решением открыть гостевые заказы; отсутствие хеша
его не отменяет. Настройки доступа читаются только из ENV, не из iiko JSON.
Они не сериализуются Config. `BEINI_TESTER_LOCAL_HTTP` — пусто/0 либо1.

Для HTTPS требуется точный ALLOWED_ORIGINS, например оба beinirest.ru имени.
В cookie нет Domain: вход на apex не авторизует www и наоборот. Используйте
одно выбранное имя для входа и оформления. Go-порт не публикуйте; Nginx
перезаписывает Host/X-Forwarded-Proto/IP. Прямой HTTP `/api/access` на loopback
без HTTPS/proxy-контекста отвечает503, это не поломка health/menu.

### Создание и смена пароля

На доверенной машине с Go1.24+ и Python3.10+ выполните:

```sh
python scripts/tester-password.py --output PRIVATE_HASH_FILE
```

Вместо PRIVATE_HASH_FILE задайте **новый** файл в существующем закрытом каталоге
вне checkout и STATIC_DIR. Утилита дважды запрашивает пароль скрыто, передаёт
его stdin в `cmd/password-hash`, пишет только PBKDF2-хеш в файл0600 и не выводит
пароль/хеш в терминал. На Windows отдельно ограничьте ACL. Минимум12 и
максимум1024 байт; используйте длинный уникальный пароль, отдельный от mock.
Низкоуровневый `go run ./cmd/password-hash` читает stdin и пишет хеш stdout:
не передавайте пароль в аргументах, history или логируемом pipeline.

Для systemd создайте fragment с `--env` в новом закрытом файле. Передайте его
защищённо как `/etc/beini/tester.env`, root:beini0640, каталог0750. Шаблон unit
читает этот дополнительный EnvironmentFile после service.env; в Git его нет.
Не добавляйте пустые/примерные реальные хеши в tracked ENV-шаблон.
Сам пароль вводит и хранит владелец, в переписку его передавать не требуется.

После отдельного поручения на настройку/перезапуск:
задайте `BEINI_ORDER_MODE=tester`, установите tester.env и обновлённый unit,
выполните systemd-analyze verify/daemon-reload, перезапустите **только beini**.
Откройте HTTPS `/tester`, войдите, перейдите к обычному меню. Вход не создаёт
заказ; предупреждение реальной отправки появляется до финальной кнопки.

Для смены пароля создайте новый хеш, замените только закрытый tester.env,
перезапустите beini. Для отзыва доступа удалите hash из серверной конфигурации
и/или поставьте closed с restart. Журналы сохраняйте. Logout отзывает текущую
сессию браузера, включая его вкладки; restart/смена хеша отзывают все сессии.

### Сессия, повтор и смена режима

Сессия действует8ч, без скользящего продления. Cookie HttpOnly/Secure/Strict,
привязана к host и Path=/; на сервере хранится только SHA256 случайного ID.
Сессии в памяти: после restart нужен повторный вход. Вход ограничен глобально
5 попытками/минуту и2 параллельными вычислениями; при429 подождите Retry-After.
Перезапуск ради обхода limiter не является штатным способом входа.

GET `/api/access` персонален, no-store/Vary Cookie, возвращает CSRF на2ч.
Login/logout/order требуют same-origin JSON и X-CSRF-Token. Секретов в URL,
localStorage и логах нет; локально остаются корзина и прежний key/body заказа.
Новая попытка требует Web Locks; неподдерживающий браузер предлагает обновить
его или позвонить. Выход в другой вкладке обновляет гостевое состояние.

Смена режима — изменение BEINI_ORDER_MODE и restart **того же** приложения
с **тем же** BEINI_STATE_DIR, без второго writer. В closed/tester-guest POST
заказа запрещён, включая точный повтор; GET статуса по приватному прежнему
Idempotency-Key работает без входа. Pending worker продолжает сверку.
После истечения сессии/выхода refresh не очищает key/body и не создаёт новую
попытку. Войдите заново, проверьте статус; при unknown/404 используйте явную
кнопку повтора с прежним ключом. При pending не оформляйте второй заказ.
При confirmed/rejected тело с контактами удаляется из browser attempt.

`/api/menu.orderingAvailable` означает только свежесть/допуск каталога;
авторизация определяется отдельно `/api/access.canOrder`. Свежие стопы и меню
не доказывают приём кассой. Вход не обходит цену, стоп, состав или свежесть.

### Ежедневная offline-разработка

```sh
python scripts/mock-ui.py --password-hash-file PRIVATE_DEV_HASH_FILE
```

PRIVATE_DEV_HASH_FILE — отдельный dev-хеш, созданный описанной утилитой без
`--env`. Порт8765, прямой127.0.0.1; реальный iiko config не читается. Без аргумента
работает гостевая витрина и отключён вход. `/tester` использует учебный пароль.
MOCK виден в плашке, форме и результате; даже success не означает приём рестораном.
Память fixture теряется при restart. Надёжность журнала проверяется Go-тестами.

Менять сценарии можно локальной утилитой (JSON заключите в одинарные кавычки):

```sh
python scripts/mock-control.py '{"status":"pending"}'
python scripts/mock-control.py '{"status":"confirmed"}'
python scripts/mock-control.py '{"status":"rejected"}'
python scripts/mock-control.py '{"drop":true}'
python scripts/mock-control.py '{"dropBefore":true}'
python scripts/mock-control.py '{"expireSessions":true}'
python scripts/mock-control.py '{"mode":"closed"}'
```

`drop` теряет ответ после записи, `dropBefore` — до неё (GET404, явный повтор).
`creates` в выводе растёт только при новой синтетической попытке; повтор не
увеличивает счётчик. Дополнительно доступны price/menuAvailable/menuError/stopIds.
`--port` выбирает другой loopback-порт. Утилита проверяет mock=true и никогда
не обращается к публичному origin. `/__mock__` отсутствует в production.

Для разработки именно Go HTTP через localhost нужны server-only hash,
`BEINI_ORDER_MODE=tester`, `BEINI_TESTER_LOCAL_HTTP=1`, прямой loopback и mock
transport. Например в PowerShell хеш читается без вывода:
`$env:BEINI_TESTER_PASSWORD_HASH = (Get-Content PRIVATE_DEV_HASH_FILE -Raw).Trim()`.
**LocalHTTP не превращает боевые ключи в mock.** Безопасный ежедневный UI запуск
— Python fixture, полный backend checkout — Go httptest. Не запускайте второе
приложение с боевыми настройками той же организации для тестирования.

Реальная приёмка после отдельного поручения: сотрудник присутствует → согласован
один заказ → owner checkout → проверка карточки, состава, суммы, сигнала/печати
на iikoFront → отмена сотрудником. Отдельно зафиксировать кассовый результат;
mock success и свежесть меню не заменяют эту последовательность.
