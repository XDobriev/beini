# Серверная синхронизация меню iiko

Срез интеграционной версии: 1 ноября 2026. Компоненты подключены в
`cmd/server/application.go`; GET /api/menu и серверная валидация используют один Store.
Frontend получает меню и свежесть. Проверено с mock API, внешних настроек не меняли.

## Источники и проверка документации

Публичная официальная OpenAPI получена GET без ключей и запросов к ресторану.
[Сверка схемы](iiko-schema-review-2026-11-01.md) содержит источник, SHA-256 и выводы.
Исправлены `terminalGroupsIds`, строчные типы `dish`/`good` и `useBalanceForSell`.
Метод `/api/1/nomenclature` в текущей схеме помечен deprecated; автоматического
переключения на `api/menu/v3/by_id` нет. Для миграции нужен отдельный адаптер и выбор
меню/ценовой категории. Текущая схема `/api/2/menu` не является нашим контрактом.
Fixtures остаются синтетическими, теперь учитывают проверенные поля OpenAPI.
Поддержку и полноту меню ресторана, а также число исключённых блюд ещё нужно
проверить согласованным read-only ответом. В этой задаче к ресторану не обращались.

Номенклатура запрашивается целиком: `organizationId`, `startRevision: 0`.
Обязательны неотрицательный `revision`, непустой `products`, уникальные `id`,
булевый `isDeleted`, а у активного продукта — `name`, `type`, непустой `sizePrices`.
У каждой цены обязательны числовой конечный неотрицательный `currentPrice` и
булевый `isIncludedInMenu`. Отсутствующие поля и неверные типы не означают пустое меню.
Регрессия `revision` отвергается, повтор той же ревизии допускается и обновляет
время успешной проверки. Пустая номенклатура отвергается как потенциальная ошибка:
чтобы временно закрыть всё меню, нужен корректный полный ответ со стопами/удалениями.

Стоп-лист запрашивается с `organizationIds`, `terminalGroupsIds`, `returnSize: false`.
Ожидаемая вложенность:

```json
{
  "terminalGroupStopLists": [{
    "organizationId": "org",
    "items": [{
      "terminalGroupId": "terminal",
      "items": [{"productId": "product-uuid", "balance": 0}]
    }]
  }]
}
```

Выбирается ровно одна организация и одна терминальная группа. Сведения других
групп не объединяются. Только явное `items: []` выбранной группы означает пустой
стоп-лист. Отсутствие группы, `null`, пропуск `balance`, дубликаты, размерные
остатки и повреждённый JSON — ошибки, сохраняющие последний успешный снимок.
`balance <= 0` блокирует блюдо; положительный остаток допускает продажу.
Это проверка доступности, а не резервирование и не контроль количества порций
по остаткам: если нужен такой контроль, потребуется отдельное изменение заказа.

## Единый каталог и правила публикации

`catalog.ReadSeed` загружает `data/menu_catalog.json` как проверенный редакционный
allowlist. Серверный `catalog.Store` содержит и цены для заказа, и поля витрины.
`Store` реализует существующий `catalog.Catalog`; `FindProduct` принимает локальный
ID или iiko ID без учёта регистра, возвращает только доступные свежие позиции.
`Store.Pin()` фиксирует одну версию и решение о свежести для всего заказа.

Сохраняются локальные ID, названия, описания, фото, вес как витринный текст,
категории, их порядок, badge и isHalal. Обновляются доверенная цена и доступность.
Новые позиции iiko не попадают в снимок до ручного добавления в allowlist.
`available: false` в seed — редакционный запрет, он не снимается синхронизацией.
Не используйте в seed результат старого импорта со случайно сохранёнными стопами
без ревью: редакционные запреты и временные стопы теперь имеют разные роли.

Поддерживаются `dish`/`good` (без учёта регистра), одна цена без размера, `isIncludedInMenu: true`,
положительная цена. Весовая продажа (`useBalanceForSell`), открытая цена (`canSetOpenPrice`),
compound, любые модификаторы и размерные варианты
остаются недоступными: текущий заказ не передаёт размеры и модификаторы.
Удалённые, исчезнувшие и непродаваемые позиции сохраняются в снимке как
недоступные; их редакционные поля не теряются. Обновление только стоп-листа
не возвращает в продажу редакционно скрытую или неподдерживаемую позицию.

Полное обновление получает и проверяет **меню и свежий стоп-лист**, строит
целый снимок, записывает его на диск и только затем публикует в памяти.
Ошибка любого шага оставляет предыдущую версию. Более частое обновление
стоп-листа использует прежние цены и меняет целиком снимок доступности,
не продлевая свежесть номенклатуры.

Запись: временный файл рядом с целевым → `Sync` → `Close` → `Rename` →
публикация в `Store`. Исходный файл не удаляется перед заменой. Кэш содержит
снимок и SHA-256; это защита от повреждения, не подпись против владельца файловой
системы. При рестарте `Restore()` проверяет checksum, схему, организацию, терминал,
время и digest allowlist; изменённый seed требует нового полного обновления.
Кэш с другими ID, будущим временем или повреждением не публикуется. Проверено
восстановление после обычного рестарта процесса; гарантия при потере питания
диска отдельно не проверялась. Нужны локальная файловая система и один writer
на один `Store`/кэш. Несколько процессов и сетевые файловые системы не поддержаны.

## Расписание, свежесть и ошибки

Все интервалы передаются явно, без скрытых глобальных настроек:
- `menusync.Config.MenuInterval`, `StopListInterval` — периоды опроса;
- `RequestTimeout` — предел каждого запроса к источнику;
- `catalog.NewStore(menuMaxAge, stopMaxAge)` — независимые пределы свежести.

`Run(ctx)` сразу выполняет полное обновление, затем опрашивает источники
по расписанию. Обновления сериализованы. До первого снимка ошибка старта
повторяется на коротком интервале стоп-листа. `ctx.Cancel()` останавливает
polling и активный HTTP-запрос; приложение должно дождаться завершения goroutine.

Пример для подключения: меню каждые 15 минут, стопы каждую минуту; свежесть
меню 2 часа, стопов 5 минут; timeout 20 секунд. Это параметры примера,
а не подтверждённые лимиты iiko — сверить частоту с лицензией и ограничениями API.

Снимок считается просроченным при `age >= maxAge`, при нулевом времени
или переводе часов назад за время успешной проверки. Ошибка не меняет timestamp
последнего успеха и не обнуляет стопы. Пока прежние данные свежие, применяется
их доступность. После просрочки любого источника `orderingAvailable: false`,
все публичные `available: false`, поиск для заказа ничего не разрешает.
Содержимое меню остаётся доступным для просмотра. Нет успешного снимка — HTTP 503.

`menuUpdatedAt` и `stopListUpdatedAt` — время последней успешно опубликованной
проверки соответствующего источника (UTC, RFC3339); восстанавливаются из кэша.
`updatedAt` — время успешной публикации снимка. `version` увеличивается при каждой
публикации, включая стоп-лист; `revision` — ревизия номенклатуры iiko.
`menuStatus` и `stopListStatus` содержат время последней попытки и безопасный код
последней ошибки. Они живут в памяти текущего процесса и очищаются после успеха;
история ошибок через рестарт не сохраняется. Для долговременного наблюдения
интегратор может периодически писать эти коды в имеющийся logger/мониторинг.

Коды: `menu_fetch_failed`, `menu_invalid`, `menu_revision_regressed`,
`stop_list_failed`, `menu_not_initialized`, `snapshot_publish_failed`,
`snapshot_restore_failed`, `cancelled`. Тела ошибок iiko, токены и credentials
не включаются в этот статус или JSON. HTTP 401/429/5xx, неверный JSON,
ошибочный envelope и timeout не публикуются. Автоматических сетевых retry
внутри одного запроса нет; следующая попытка — по расписанию. Redirect запрещён.

## JSON для frontend

`menusync.MenuHandler(store)` зарегистрирован на `GET /api/menu`.
Он читает память, не обращается к iiko. `Content-Type: application/json; charset=utf-8`,
`Cache-Control: no-store`. Другие методы — 405 с `Allow: GET`.
Пока нет снимка: 503 `{"error":"menu_unavailable"}`. Со старым снимком — 200,
его данные и флаги просрочки. Форма успешного ответа (поля отдельного Item
без значения, например `badge`, могут отсутствовать):

```json
{
  "schemaVersion": 1,
  "version": 42,
  "revision": 7,
  "organizationId": "org",
  "terminalGroupId": "terminal",
  "seedDigest": "sha256-of-reviewed-seed",
  "updatedAt": "2026-11-01T10:00:00Z",
  "menuUpdatedAt": "2026-11-01T09:50:00Z",
  "stopListUpdatedAt": "2026-11-01T10:00:00Z",
  "categories": [{"id":"grill","name":"Мангал","icon":"flame","sortOrder":2}],
  "items": [{
    "id":"beini-grill-01",
    "iikoId":"11111111-1111-4111-8111-111111111111",
    "name":"Редакторское название",
    "description":"Сохранённое описание",
    "image":"assets/images/dishes/example.jpg",
    "weight":"410 г",
    "price":620,
    "category":"grill",
    "isHalal":true,
    "sellable":true,
    "available":false,
    "unavailableReason":"stop_list"
  }],
  "menuStale":false,
  "stopListStale":false,
  "orderingAvailable":true,
  "menuStatus":{"lastAttemptAt":"2026-11-01T09:50:00Z"},
  "stopListStatus":{"lastAttemptAt":"2026-11-01T10:01:00Z","lastError":"stop_list_failed"}
}
```

Frontend группирует `items` по `category`, сохраняет порядок массивов, разрешает
добавление только при `orderingAvailable && item.available`. При просрочке
показывает давность и не предлагает checkout; при 503 показывает недоступность
меню. `unavailableReason` — `stop_list` или `not_sellable`; при просрочке причина
находится в общих флагах. `sellable` и `seedDigest` — служебные поля, не основания
для гостевой доступности. Ошибка последнего опроса и просрочка различаются.
Пустой `lastAttemptAt` после восстановления имеет стандартное нулевое время Go;
оно не означает свежую проверку. Денежная единица — рубли, `price` — JSON number.

Перед отправкой витрина передаёт ожидаемые цены каждой строки. Сервер фиксирует
снимок один раз, сверяет цены и при расхождении возвращает 409 без Reserve/create.
Гость видит новые цены/сумму и подтверждает их явно. Подробности в
[обработке заказов](order-processing.md).

## Подключение приложения

`cmd/server/application.go` загружает reviewed seed, создаёт один Store и один Service
с токеном существующего клиента, восстанавливает кэш и запускает worker. Тот же Store
передан единственному handler, который делает Pin на новый заказ (не на каждый GET
и не на весь срок жизни handler). До успешного снимка доступен только просмотр.
Кэш расположен в BEINI_STATE_DIR вне web root, worker останавливается и ожидается
при shutdown. Legacy latte/p1 не добавлены в allowlist; fixed test-order отключён.

## Импортёр и offline-проверки

`tools/import_menu.py --check` остаётся полностью локальным. `--from-file` без
стоп-листа означает **неизвестную** доступность: отсутствует сообщение о чистом
стоп-листе, прежние запреты не снимаются. Для fixture стоп-листа:

```sh
python tools/import_menu.py --from-file internal/menusync/testdata/nomenclature.json --stop-list-file internal/menusync/testdata/stop_lists.json --organization-id org --terminal-group-id terminal
```

Эти synthetic ID не соответствуют локальному меню: команда нужна для проверки
формата и dry-run, не для `--apply`. Legacy `--apply` сохраняет редакционные поля,
не добавляет новинки, скрывает удалённые и неподдерживаемые блюда и никогда
автоматически не снимает прежний `available:false`. JSON и JS по-прежнему
экспортируются как файлы, это не runtime worker и не замена его кэша.

Автопроверки используют fixtures, `httptest` и временные каталоги, без ключей и
сетевых обращений к iiko:

```sh
python scripts/check.py
go test -race -timeout 60s ./internal/catalog ./internal/menusync
```

Покрыты: scope терминала, пустой/неизвестный стоп-лист, ошибки HTTP 401/429/500,
повреждённый JSON/схема, timeout, регрессия ревизии, скрытые/новые/неподдерживаемые
позиции, сохранение фото и текстов, ошибка диска, checksum и восстановление после
рестарта, просрочка обоих источников, конкурентные читатели, независимые интервалы,
завершение по context и HTTP-контракт. Результаты фактических запусков см. в
[передаче задачи](tasks/menu-sync-2026-11-01.md).
